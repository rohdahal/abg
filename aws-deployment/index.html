What Phase 3 set out to do

Until now, ABG Hub existed on one Windows PC in the office. If that machine was asleep, switched off, or being used for something else, the system was unavailable. Backups, updates and recovery all depended on that one box continuing to work.

Phase 3 removes that dependency. The application moved into AWS, the files moved with it, and the process for shipping a change became a repeatable pipeline instead of a manual routine carried out on the office machine.

Where the application runs now

Three pieces, each doing one job, none of them a machine anybody has to look after.

The API
AWS Lambda, container image
The application is packaged as a container and run on demand. There is no server to keep running, no operating system to patch, and nothing to restart after a power cut. It costs nothing while nobody is using it.
The web interface
Amazon S3 and CloudFront
The part that runs in the browser is published as static files and delivered from AWS's global network, so it loads quickly and stays available independently of the API.
The data and the files
RDS PostgreSQL and S3
Visit photos, signatures, ticket attachments and generated PDFs now live in S3 rather than on a desktop hard drive. The same code still writes to local disk when a developer runs it on their own machine.
The release process
GitHub Actions and AWS
The steps that put a change live are written down and run the same way every time, so a release is a repeatable procedure rather than a person remembering an order.

How a change reaches production

Pushing to the main branch of the repository is the whole procedure. A pipeline then does the same four things, in the same order, every time.

  • 1Database changes are applied first, by a migration tool that records what it has already run, so the same change is never applied twice and the order is never in doubt.
  • 2The API is rebuilt and released, and the pipeline waits for AWS to confirm the new version is live before it continues.
  • 3The web interface is published and the cache is cleared, so nobody is left looking at yesterday's version.
  • 4Only what changed is deployed. A change to the web interface alone does not rebuild the API or touch the database.

No passwords are stored in the pipeline. It authenticates to AWS with short-lived credentials issued for each individual run and expiring immediately afterwards. There is no long-lived key that could be copied out of the repository, and nothing to rotate.

What this removes

Five things tied ABG Hub to that specific PC. Phase 3 addresses the ones that stood between the application and a server.

  • ✓Uploaded files no longer live on a desktop. Photos, signatures, attachments and PDFs are in cloud storage, backed up and reachable from anywhere.
  • ✓The application no longer needs Windows. It runs on Linux in AWS, which is what made a serverless deployment possible at all.
  • ✓Releasing no longer happens on the office machine. It happens in the repository, with a record of who released what and when.
  • ✓The spreadsheet sync no longer depends on one person's browser sign-in, having been moved onto credentials that belong to the organisation rather than to a machine.

The office PC stays exactly as it is, untouched, as a fallback. Nothing about this phase required switching it off, and nothing was removed from it.

What Phase 3 left for later

The system was in AWS and working, but two things were deliberately left until the account matured. The first time the system was used after a quiet period it took a few seconds to wake, because AWS had capped how much processing power the account could request. The second was the public web address: the Hub was reachable at an AWS-provided address, with the permanent one still to come.

Both were dealt with in the phases that followed, along with the work that turned the deployed system into the CRM the office uses day to day.
