ABG Hub · Cloud Deployment

Delivery Record

ABG Hub used to run entirely on one Windows PC in the office: the application, the database and every uploaded file. If that machine was asleep, the business had no system. The public website belonged to an outside website builder, on hosting and a domain the company did not control.

Both now run in ABG's own AWS account. Staff reach the Hub from anywhere, updates deploy themselves, and the website can be edited by an administrator without a developer. Nothing was lost in the move, and staff were never without the system.

What was delivered

A summary of each phase. Click the button at the end of each one to read it in full.

  1. Phase 1 Database Migration to AWS Complete

    The company's data moved from the SQL Server on the office PC to a managed PostgreSQL database on AWS, where it is backed up and reachable from anywhere.

    • A purpose-built copying tool that checks its own work, comparing every table's row count and every link between tables before it reports success.
    • 27,580 records across 33 tables carried across, and independently confirmed afterwards.
    • Database hosting at roughly $14 a month, against about $400 a month for the equivalent on the old engine.
    12 August 2026 · run by the client from the office · verified remotely
    Read the full Phase 1 →
  2. Phase 2 Application Migration to PostgreSQL Complete

    The application itself was rewritten to speak to the new database, and packaged so it starts on any computer with a single command rather than only on the office PC.

    • Around 50 places in the code that assumed the old database were reworked. Searching still ignores capital letters the way the office expects.
    • All 76 places the system reads data were checked against the live cloud database.
    • 94 automated tests were added. They run against a real database every time the code changes, so an old assumption cannot creep back in unnoticed.
    13 August to 1 September 2026 · no change visible to staff
    Read the full Phase 2 →
  3. Phase 3 Application Deployment to AWS Complete

    The Hub left the office PC. It now runs in AWS with no server for anyone to maintain, and a change reaches production by being published rather than by somebody being at a particular desk.

    • The application runs on demand and costs nothing while nobody is using it.
    • Photos, signatures, attachments and generated PDFs moved from a desktop hard drive into cloud storage.
    • Releasing became a repeatable process that runs in the same order every time, and only updates the parts that actually changed.
    • The release process holds no passwords. It is given temporary access each time it runs, and that access expires straight afterwards, so there is nothing stored that could be copied.
    10 September 2026 · office PC left untouched as a fallback
    Read the full Phase 3 →
  4. Phase 4 CRM Hub Launch Complete

    With the system in the cloud, what it could not yet do became the limit. This phase turned it into the CRM the office uses daily.

    • People are invited by email and set their own password from a link valid for seven days. Nobody handles anybody else's password, and invitations can be revoked or reissued.
    • Weekly report drafts are created directly in a Microsoft 365 mailbox. This removed the last reason the system needed a Windows machine with Outlook installed.
    • The dashboard was rebuilt around what needs attention today, with charts drawn from what the team actually recorded and a running list of recent activity.
    • Task handling was reworked with due dates and clearer statuses. The whole interface was refreshed at the same time, including a sidebar that works on a phone.
    13 to 17 September 2026 · delivered as one reviewed change · 77 automated checks passed
    Read the full Phase 4 →
  5. Phase 5 The Website Moves to AWS Complete

    The public website looked like a company asset but was not one. It was produced by an outside builder, hosted on their infrastructure, with the domain administered from an account nobody at ABG could sign in to. This phase brought all of it under company ownership.

    • A faithful copy of the live site was captured and published to ABG's own storage, delivered through AWS's global network. Visitors saw no change, which was the intention.
    • The domain settings moved to a service the company controls. The old settings were written down first, so they could be put back exactly if anything went wrong.
    • Email was protected throughout. The records that route and authenticate company mail were identified in advance, checked after the move, and confirmed by querying the public record independently.
    • Search visibility carried across: the same addresses, titles and descriptions, with the site map kept current automatically.
    12 to 22 September 2026 · no site downtime · no interruption to mail
    Read the full Phase 5 →
  6. Phase 6 Website Studio Complete

    Owning the website is not the same as being able to change it. Website Studio puts the public site inside ABG Hub, so an administrator can edit it and publish it without a developer.

    • Edit a page in the Hub with a live preview of the real page beside it.
    • Publishing first puts the change on a private copy of the site that the public cannot find and search engines ignore. Only a reviewed version can go to the live site.
    • The last five published versions are kept in full, so going back is immediate rather than a reconstruction, and the editor returns with it.
    • Pictures upload straight from the browser, and the Studio reports any search wording that did not follow a change rather than leaving it stale and unmentioned.
    22 September 2026 · open for the client's team to review

What ABG owns now

The application, the database, the uploaded files, the public website, the domain and the process that deploys all of it sit in accounts the company controls. Nothing depends on a single machine, a single person, or an outside supplier. The office PC was left exactly as it was throughout, untouched, as a fallback that was never needed.

One item remains open, and it is waiting on AWS rather than on work. The delivery network in front of the website runs in a supplier account, because AWS had not yet cleared ABG's own account for that service when it was needed. Moving it across is a documented, contained change. It is worth following up with AWS support periodically, as the restriction lifts with account history rather than on request.
