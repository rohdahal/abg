What Phase 2 set out to do

Phase 1 moved the data. Phase 2 moves the application that reads it.

Until now the software spoke only to SQL Server, the database that runs on the office PC. Phase 2 rewrites the parts of the application that talk to the database so they speak to PostgreSQL instead, the open engine chosen for the cloud. The reason is cost: PostgreSQL carries no licence fee, which keeps hosting near fourteen dollars a month rather than the several hundred a licensed SQL Server would demand.

The important promise is that this is invisible. Every screen, report, and number the staff see is unchanged. What changed sits underneath, in the language the application uses to ask the database questions.

What changed underneath

The two databases are close cousins, not twins. Around fifty places assumed SQL Server, and each was translated.

Query language

SQL Server and PostgreSQL phrase the same request differently. Each pattern was translated to its PostgreSQL equivalent and checked against real data.

Case-insensitive matching, preserved exactly

On the office database, searching for ADMIN, admin or Admin returns the same result, because SQL Server ignores letter case by default. PostgreSQL does not. Left unaddressed, a manager searching by status or name would quietly get fewer results than before, with no error to signal it.

This was fixed at the foundation rather than patched search by search: 39 columns (the status, role and name fields, among others) now use a case-insensitive column type, so the database itself treats case the way the office always has. It even continues to reject a duplicate Admin next to an existing admin, exactly as before.

The spreadsheet sync, rewritten in step

A separate routine keeps the system in step with Google Sheets and talked to SQL Server directly, bypassing the rest of the application. It was ported alongside everything else, so the nightly sync behaves identically on the new engine.

A note on method Rather than reason about what might break, a local copy of PostgreSQL was loaded with the real 27,600 rows and every screen was exercised against it. That turned guesswork into a concrete list of issues to fix, and it is how subtle differences (a search returning too few rows, results sorted in a different order) were caught before the client ever saw them.

How it runs now

The application no longer needs a hand-built machine. It runs the same way on any Windows or Mac computer.

Everything the application needs, the database, the interface and the web server, is packaged together with Docker. Once Docker Desktop is installed, the whole system starts with one line:

$ docker compose up -d

The database builds its own structure on first start, the interface appears in a browser, and there is nothing to configure by hand. A short, illustrated guide covers installing Docker Desktop and running these steps on both Windows and Mac. A second command loads a live copy of the real data from the cloud whenever a working set is needed.

Verified, not assumed

Phase 2 was signed off against a real cloud database, not a developer's guess. Each of these was checked directly.

  • ✓The full database structure (33 tables) builds itself on a fresh start.
  • ✓Reports keep their exact spreadsheet headings and their MM/DD/YYYY dates.
  • ✓Every store still reconciles: 1,094 and 1,832 vendor rows account for all 2,926 stores.
  • ✓Case-insensitive search returns what the office expects, confirmed against the old behaviour.
  • ✓A clean start on a bare machine was rehearsed end to end: database, interface and web app all came up from nothing.

A safety net for what comes next

A new suite of 94 automated tests now runs every database statement against a real PostgreSQL server, on every change. Its job is to catch any SQL Server assumption that slips back in before it can reach the client. It was proven to work by deliberately reintroducing an old pattern and watching the tests fail.

What Phase 2 leaves for later

Two phases remain, and one item is deliberately staged for the next.

The application is ready to run in the cloud, but for now it is still started by hand and keeps uploaded files (photos, signatures, PDFs) on local disk. Phase 3 gives it a permanent home on a small cloud server, moves those files to cloud storage, and replaces the last few things that only a Windows office PC can do today, chiefly the weekly report emails. Phase 4 is the final switch, with the office PC kept untouched as a fallback for a full working cycle before it is retired.

Each phase stays reversible until that last step, so there is no point before cutover where the office system cannot simply carry on.
