Database Migration to AWS

ABG Hub's database moved from a single office PC to a managed cloud database. This was the foundation everything else was built on, and the only phase that touched live business data.

Why the database went first

Nothing else could be built until the data had somewhere to live.

ABG Hub kept everything on one machine in the office: the database, the application, and the uploaded files. That machine was the single point of failure for the entire business system. If it was off, stolen, or its disk failed, the membership records went with it.

Moving the database out first meant the records were backed up and reachable from anywhere before any other change was made. It was also the only phase that moved real data, so it was done carefully and on its own, rather than bundled into a larger cutover.

Database choice

Same capability, without the licence.

The office system ran SQL Server. Keeping SQL Server in the cloud was possible but expensive: on AWS the licence is bundled into the hourly rate and cannot be avoided. PostgreSQL was the closest equivalent with no licence cost at all, and no ceiling on database size.

Translation work done first

The schema was rebuilt for PostgreSQL and checked table by table against the office database. Two differences mattered more than the rest:

  • Text matching. SQL Server treats ADMIN@abg.com and admin@abg.com as the same value. PostgreSQL does not. Eighteen columns (every email address, ABG number, state code and vendor name) were given types that ignore capitals, so that logging in and duplicate-checking behaved exactly as they had before.
  • Two missing tables. Neither the existing setup script nor the application's own model was a complete description of the schema. Each was missing a table the other had. Both are now present in the cloud database.

How the migration ran

Four steps on the day. Only one of them happened in the office.

  1. Update the office project folder
    Office · 1 minute
    Pulled down the migration tooling. No change to the application itself.
  2. Connection test
    Office · 1 minute · changed nothing
    Confirmed the office database was readable, the cloud database reachable, the two schemas in agreement, and the data consistent. Nothing was written in this step, so there was nothing to undo if it failed.
  3. Data copy
    Office · minutes, depending on connection speed
    Required the ABG Hub window to be closed first, so that no record changed mid-copy. The copy then verified itself, checking every table's row count and every relationship between tables, before reporting success.
  4. Verification
    Remote · no office involvement
    Each run recorded its own outcome inside the cloud database, so the result was confirmed independently rather than by someone reading a screen.

Safeguards

The office system stayed the system of record until the cutover, and was treated as such.

Nothing on the office machine was changed

Every instruction sent to the office database was a read. There was no delete, update, insert or clear operation anywhere in the process, on any path, including error paths. No files were moved and nothing was cleaned up afterwards.

Safe to repeat

Each run replaced the cloud copy in full rather than adding to it, so an interrupted or failed attempt was fixed by running it again. There was no half-finished state to reason about.

It stopped rather than guessed

If the office database had appeared empty, if records had been found pointing at records that no longer existed, or if the two schemas had disagreed in a way that would lose data, the run would have halted before writing anything and reported what it found.

Access was temporary

The office machine connected using a credential created solely for this copy and limited to this one database, so it granted nothing beyond what the copy needed.

What this phase left out

Deliberately deferred, and tracked.

  • Uploaded files. Visit photographs, signature images and ticket attachments were stored as files on the office machine rather than inside the database, so they were not part of this copy. They moved in Phase 3, when the application itself moved and needed somewhere to read them from.
  • The application. It carried on running in the office, against the office database, unchanged. Staff saw no difference during this phase.
  • Report emailing. The weekly report feature drove Outlook on the office desktop directly. That could not work on a cloud server, and was replaced in Phase 4.

Still worth tightening

  • Backup retention. Set to one day, which was the cap on the account's billing plan at the time. Upgrading the plan raises it to seven, which is worth doing now that it holds live records rather than test data.
  • Network access. Access was left deliberately broad for the migration window, so the office could connect without its network details being known in advance. Now that the run has identified that address, it is worth locking access to it and revoking the temporary migration credential.

The copy was rehearsed end to end against the live cloud database at full scale, including attachments, with row counts and relationships checked afterwards. It was then run on the office Windows machine and has been in use since, without problems.
