Why the database goes first

Nothing else in the deployment can be built until the data has somewhere to live.

ABG Hub currently keeps everything on one machine in the office: the database, the application, and the uploaded files. That machine is the single point of failure for the entire business system. If it is off, stolen, or its disk fails, the membership records go with it.

Moving the database out first means the records are backed up and reachable from anywhere before any other change is made. It is also the only phase that moves real data, so it is worth doing carefully and on its own, rather than bundled into a larger cutover.

Database choice

Same capability, without the licence.

The office system runs SQL Server. Keeping SQL Server in the cloud is possible but expensive: on AWS the licence is bundled into the hourly rate and cannot be avoided. PostgreSQL is the closest equivalent with no licence cost at all, and no ceiling on database size.

The trade-off is that application code written for SQL Server needs translating. That work is scoped and scheduled as Phase 2. It does not block the data move, because the office system keeps running on SQL Server until the new application is ready.

Translation work already completed

The schema was rebuilt for PostgreSQL and checked table by table against the office database. Two differences mattered more than the rest:

  • Text matching. SQL Server treats ADMIN@abg.com and admin@abg.com as the same value; PostgreSQL does not. Eighteen columns (every email address, ABG number, state code and vendor name) were given case-insensitive types so that logging in and duplicate-checking behave exactly as they do today.
  • Two missing tables. Neither the existing setup script nor the application's own model was a complete description of the schema; each was missing a table the other had. Both are now present in the cloud database.

How the migration runs

Four steps on the day. Only one of them happens in the office.

  1. Update the office project folder
    Office · 1 minute
    Pulls down the migration tooling. No change to the application itself.
  2. Connection test
    Office · 1 minute · changes nothing
    Confirms the office database is readable, the cloud database is reachable, the two schemas agree, and the data is consistent. Nothing is written in this step, so there is nothing to undo if it fails.
  3. Data copy
    Office · minutes, depending on connection speed
    Requires the ABG Hub window to be closed first, so that no record changes mid-copy. The copy then verifies itself, checking every table's row count and every relationship between tables, before reporting success.
  4. Verification
    Remote · no office involvement
    Each run records its own outcome inside the cloud database, so the result can be confirmed independently rather than relying on someone reading a screen.

Safeguards

The office system is the system of record until the cutover, and is treated as such.

Nothing on the office machine is changed

Every instruction sent to the office database is a read. There is no delete, update, insert or clear operation anywhere in the process, on any path, including error paths. No files are moved and nothing is cleaned up afterwards.

Safe to repeat

Each run replaces the cloud copy in full rather than adding to it, so an interrupted or failed attempt is fixed by simply running it again. There is no half-finished state to reason about.

It stops rather than guesses

If the office database appears empty, if records are found pointing at records that no longer exist, or if the two schemas disagree in a way that would lose data, the run halts before writing anything and reports what it found.

Access is temporary

The office machine connects using a credential created solely for this copy, limited to this one database. It is revoked once the migration is confirmed, after which it grants nothing.

Not included in this phase

Deliberately deferred, and tracked.

  • Uploaded files. Visit photographs, signature images and ticket attachments are stored as files on the office machine rather than inside the database, so they are not part of this copy. They move in Phase 3, when the application itself moves and needs somewhere to read them from.
  • The application. It continues to run in the office, against the office database, unchanged. Staff see no difference during this phase.
  • Report emailing. The weekly report feature drives Outlook on the office desktop directly. That cannot work on a cloud server and needs replacing before the application moves.

Road to full deployment

This phase is the foundation; three remain.

  1. Database Migration to AWS
    Current phase
    Cloud database live, tested, awaiting the office run.
  2. Application Migration to PostgreSQL
    Next · estimated 2–3 days · nothing visible to staff
    Around fifty places in the application still expect the old database and have to be reworked. The work is mechanical rather than uncertain, and each change is tested against a copy of the real data rather than a test fixture. Staff carry on using the office system throughout.
  3. Application Deployment to AWS
    Scoping
    The application moves off the office PC onto a server, reached through a proper web address with a security certificate. Three things have to be rebuilt on the way, because they currently depend on that one machine: uploaded photographs and signatures move to cloud storage, the weekly report emails move off desktop Outlook, and the overnight sync job moves onto the server. Runs alongside the office system, not instead of it.
  4. Production Cutover
    Scheduled with the office
    A final data copy, then staff switch to the hosted application and the office PC stops being the system of record. It stays available, untouched, as a fallback until the new system has proven itself over a full working cycle. Backups, monitoring and access are tightened at this point, when there is live data to protect.

Open items

  • Backup retention. Currently one day, which is the cap on the account's present billing plan. Upgrading raises it to seven, which is the minimum this deserves once it holds live records rather than test data.
  • Network access. Access is deliberately broad for the migration window, so that the office can connect without its network details being known in advance. It gets locked to the office address once the first successful run identifies it, and the temporary credential is revoked at the same time.
  • Untested on Windows. The tooling has been proven end to end, but on a Mac. The office machine is the first Windows run.

The copy has been rehearsed end to end against the live cloud database at full scale, including attachments, with row counts and relationships checked afterwards. Duration in the office will depend on the size of the real dataset and the speed of the office internet connection.
